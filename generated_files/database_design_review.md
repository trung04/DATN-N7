# Database schema v1 design review

## Authoritative artifact

[`postgres_schema_v1.sql`](./postgres_schema_v1.sql) is the complete executable schema for a new database. The older `postgres_core_schema.sql` is retained only as the pre-booking design and must not be applied together with v1.

Schema v1 contains 27 tables covering:

- users, Google/password authentication state, tourists, hotel owners, and images;
- travel preferences and topics;
- sparse place ingestion, categories, topics, images, reference prices, text search, and geospatial search;
- hotels, rooms, amenities, and ownership/approval state;
- versioned booking-cancellation policy terms;
- bookings, room reservations, payment, refund, partner settlement, and overlap protection;
- itineraries, stopovers, and activities.

Reviews are intentionally outside v1 because no approved review lifecycle was supplied.

## Sparse place catalogue

`places` is not a copy of a map provider's worldwide catalogue. It stores only:

1. manually curated places;
2. legally obtained crawled places selected for display; and
3. provider search results after a user selects them through the application.

Provider search results that are only viewed remain external. Before a selected result is referenced by a stopover, the application upserts a local `places` row using `(source_provider, provider_place_id)`, assigns approved place categories, and then stores the local UUID in `stopovers.place_id`.

`provider_place_id` is `text`, not `varchar(255)`, and its uniqueness is provider-scoped. For Nominatim data, the application must not use Nominatim's internal `place_id` as a durable provider identifier; use the appropriate stable provider reference available for that source.

Source, attribution, licence, refresh time, and source URL fields preserve provenance. Their presence does not grant a right to scrape or retain provider content; ingestion must still enforce each source's current licence and retention rules.

## Geospatial and search support

`places.location` is a stored PostGIS `geography(Point, 4326)` generated from required latitude/longitude coordinates. A partial GiST index supports active-place radius and nearest-place queries. A generated `tsvector` and partial GIN index support local text search.

Place type restrictions such as `HOTEL`, `SIGHTSEEING`, `HISTORIC`, and `TRADITIONAL` belong in `place_categories` and `place_category_mappings`. The ingestion service must accept only product-approved category mappings.

## Booking and financial lifecycle

One booking row contains the final state of its single payment, optional single refund, and optional single partner settlement. Failed provider attempts are not persisted as separate financial records in v1.

Global unique indexes protect successful provider transaction IDs. Row checks require the timestamps and monetary fields needed by `PAID`, `REFUNDED`, `NOT_ELIGIBLE`, and `SETTLED` terminal states.

`booking_rooms` stores room, price, occupancy, stay-date, and currency snapshots. Its subtotal is generated by PostgreSQL. Composite foreign keys guarantee that every selected room belongs to the booking's hotel and uses the booking's dates and currency.

The `btree_gist` exclusion constraint prevents overlapping `HELD` or `CONFIRMED` reservations for the same room. Expired pending reservations do not release themselves; an application job must change their reservation status to `RELEASED` in the same transaction that expires the booking.

## Cancellation policy

Every row in `booking_cancellation_policy_terms` is one half-open elapsed-time term:

```text
min_elapsed_minutes <= cancelled_at - payment_created_at < max_elapsed_minutes
```

A null maximum is unbounded. Terms are grouped by `(hotel_id, policy_version)`, and an exclusion constraint prevents overlapping windows within a version.

The booking stores the policy version fixed at creation. At cancellation, the application selects exactly one term, saves its ID and snapshots its window, refund percentage, and description. A composite foreign key ensures that the selected term belongs to the booking's hotel and policy version.

Used policy versions must be treated as immutable. Policy changes create a new version instead of updating historical terms.

## Service-transaction invariants

PostgreSQL enforces row-level, uniqueness, foreign-key, and overlap invariants. The booking service must enforce these aggregate/cross-row rules in one transaction:

- `bookings.total_amount` equals the sum of active `booking_rooms.subtotal`;
- adult plus child count does not exceed summed room capacity snapshots;
- booking and reservation status transitions remain synchronized;
- expired room holds are released;
- the cancellation term matches elapsed time from payment creation to cancellation;
- refund amount equals the payment total multiplied by the selected refund percentage;
- settlement occurs only after the refund outcome is final.

## Authentication state

Google/password identity, email verification, and the 2FA-enabled flag are durable user state. OTP challenges, OAuth state/nonce, refresh sessions, retry counters, and rate limits remain bounded Redis state and are not database tables.

Google identities remain globally unique after account soft deletion, preventing the same provider identity from silently creating another account.

## Deletion and history

Every table has `deleted_at`; hard deletion is rejected by a shared trigger. Foreign keys use `ON DELETE RESTRICT`. Financial transaction identifiers and booking codes remain globally unique even when a record is soft-deleted.

Normal queries must explicitly exclude soft-deleted rows. Authentication must additionally require an active user status.

## Execution and backend alignment

Run `postgres_schema_v1.sql` only against a new database. It requires PostgreSQL 13+ with `postgis`, `pgcrypto`, and `btree_gist` available.

The file is not an in-place migration. Current TypeORM entities and migrations do not yet represent the complete v1 schema, and the repository currently contains no booking module. Align those application objects with v1 through forward migrations after the booking implementation is available.
